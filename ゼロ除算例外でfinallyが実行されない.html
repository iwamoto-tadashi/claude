Claude

この現象は、「捕捉した例外を throw; で再スローし、それがどこにも捕まらず未処理(unhandled)になっている」ことが原因です。

何が起きているか

  • c = b / a で DivideByZeroException が発生
  • catch ブロックでいったん捕捉され、err.ErrLog(...) を実行後に throw; で再スロー
  • この Main が呼び出しの一番外側（エントリポイント）なので、再スローした例外を受け止める catch はもうどこにも存在しない
  • → 例外は 未処理例外（unhandled exception） になる

.NET の仕様上、例外が未処理のままプロセスの外まで到達すると、CLR は通常のスタック巻き戻し（unwind）処理を行わずに、Windows Error Reporting 通知 → プロセス強制終了、という流れになります。finally ブロックの実行は本来この「巻き戻し」の過程で行われるものなので、未処理例外の場合は finally が実行される保証がないのです（デバッガをアタッチしている場合は挙動が変わって finally が動くこともあるため、Visual Studio 上のデバッグ実行では問題が再現せず、本番の WebJob 実行でだけ発生する、というのはよくあるパターンです）。

対処法

finally に頼らず、確実に SetStatus() を呼びたい箇所は catch 側にも明示的に書くのが確実です。

catch (Exception ex)
{
    errorProc err = new errorProc();
    err.ErrLog("Program.Main", ex);
    g_statusCd = 99;

    SetStatus(); // ここで明示的に呼ぶ

    throw; // 再スローしたいなら残してOK（ただしプロセスは異常終了する）
}
finally
{
    // 正常系（catchを通らないパス）用に残す場合はフラグ等で二重実行を防ぐ
}

もしくは、そもそも WebJob の Main の外側でこれ以上例外を伝播させる必要がない（プロセスがクラッシュ扱いになる方が困る）のであれば、throw; を外して catch 内で処理を完結させれば、finally も正常に実行されます。

  • throw; を残す → プロセスは異常終了扱いになる。finally は保証されないので、SetStatus() は catch 内に書く
  • throw; を外す → 例外は Main 内で完結し、finally も正常に実行される

WebJob の運用上、「ステータスを必ず更新してから終了したい」のであれば、後者（throw; を外し、catch内でステータスを更新する）の方がシンプルで安全です。

※ この回答の「未処理例外では finally が実行されない」という説明は、後続のターン（6往復目）で誤りとして訂正されています。

あなた

今のコードだとmainで読んでいるサブルーチンで例外が発生しても同様にfinallyが通りませんか？

Claude

はい、同様に finally は通りません。ただし理由は「サブルーチンで発生したから」ではなく、前回と同じ理由です。

なぜ同じ問題になるか

例外の発生元がどこであっても（Main 直下のコードでも、呼び出しているサブルーチンの中でも）、動作の流れは同じです。

  • サブルーチン内で例外発生
  • 呼び出し元に伝播し、Main の try ブロックでキャッチされる（ここは正常に動く）
  • catch 内で err.ErrLog(...) などが実行される（ここも正常に動く）
  • throw; で再スロー
  • Main は呼び出しチェーンの一番外側（エントリポイント）なので、再スローされた例外を受け止める catch がどこにもない
  • → 未処理例外（unhandled exception）としてプロセスが異常終了し、finally の実行が保証されなくなる

つまり、例外の発生場所（Main 直下 or サブルーチン内）は関係なく、「Main の catch で throw; して再スローし、それが未処理のままプロセス外まで到達する」という構造そのものが原因です。この構造がある限り、どのメソッドで例外が発生しても同じ結果になります。

対処法（前回と同じ）

  • throw; を残すなら、catch 内で SetStatus() を明示的に呼ぶ
  • 確実に finally を通したいなら throw; を外す
catch (Exception ex)
{
    errorProc err = new errorProc();
    err.ErrLog("Program.Main", ex);
    g_statusCd = 99;

    SetStatus(); // 発生元がどこであれ、ここで確実に呼ばれる

    throw;
}

なお、サブルーチン内に独自の try-catch-finally がある場合は話が別です。そのサブルーチン内で例外がローカルに完結する（外に投げない）なら、そのサブルーチン内の finally は通常どおり実行されます。「通らない」のはあくまで、最終的に Main まで伝播して未処理になった場合の話です。

dllを共有している場合、xxxx.exe.configの設定が優先されますか？
manager.dllの関数を使っているのですが、manager.dll.configもデプロイ環境に含まれます。

Claude

はい、その認識で正しいです。実行時に読み込まれるのは xxxx.exe.config のみで、manager.dll.config は基本的に無視されます。

理由

.NET Framework の設定システム（ConfigurationManager / System.Configuration）は、AppDomain単位で設定ファイルを管理します。通常、プロセスを起動した実行アセンブリ（.exe）に対応する設定ファイル、つまり xxxx.exe.config だけが自動的にロードされ、AppDomain全体で共有されます。

manager.dll の中で ConfigurationManager.AppSettings["Key"] のような形でアクセスしている場合、それは「呼び出し元がどの実行ファイルか」に関わらず、常に現在のAppDomainの設定＝xxxx.exe.config を参照しにいきます。manager.dll.config というファイルをデプロイフォルダに置いていても、CLRはそれを自動的には読み込みません。

つまり

  • manager.dll.config に書いた設定値 → 通常は読まれない（無視される）
  • xxxx.exe.config に書いた設定値 → こちらが実際に使われる

もし複数の .exe から manager.dll を共有していて、それぞれ違う設定値を使わせたい場合は、各 xxxx.exe.config 側に manager.dll が必要とする設定項目をコピー（統合）しておく必要があります。

それでも manager.dll.config を使いたい場合

明示的にコードでロードすれば可能です。

var dllConfigPath = Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "manager.dll.config");
var configFileMap = new ExeConfigurationFileMap { ExeConfigFilePath = dllConfigPath };
var config = ConfigurationManager.OpenMappedExeConfiguration(configFileMap, ConfigurationUserLevel.None);
var value = config.AppSettings.Settings["Key"]?.Value;

ただしこれは manager.dll 側の実装次第です。manager.dll 内部で単純に ConfigurationManager.AppSettings を使っているだけなら、上記のような明示的ロードのコードをその実装自体に組み込まない限り、外側から manager.dll.config を強制的に読ませることはできません。

まとめると、デプロイ環境に manager.dll.config を含めていても、それだけでは設定は反映されず、xxxx.exe.config 側の設定が実質的に優先（というより「唯一有効」）になります。

以下のコードでweb.configにapplogの設定がなくてもnullエラーを回避できますか？

CloudBlobContainer container = blobClient.GetContainerReference(ConfigurationManager.AppSettings["applog"] ?? "applog");
Claude

はい、そのコードで回避できます。

理由

ConfigurationManager.AppSettings["key"] は、該当キーが web.config（<appSettings>）に存在しない場合、例外を投げずに null を返します。辞書アクセスのように「キーが無いと例外」という挙動ではなく、NameValueCollection の実装上、見つからない場合は単に null が返る仕様です。

したがって、

ConfigurationManager.AppSettings["applog"] ?? "applog"

は以下のように動作します。

  • web.config に <add key="applog" value="xxx" /> がある → "xxx" が使われる
  • <appSettings> セクション自体が無い、または applog キーが無い → AppSettings["applog"] は null → ?? によってデフォルト値 "applog" が使われる

なので null エラー（NullReferenceException や ArgumentNullException）は発生せず、意図通りフォールバックされます。

補足（念のため注意点）

  • value=""（空文字）で明示的に設定されている場合は null ではなく "" が返るため、?? は効かず空文字がそのまま GetContainerReference に渡ります。空文字を弾きたいなら string.IsNullOrEmpty を使う書き方の方が安全です。
var containerName = ConfigurationManager.AppSettings["applog"];
containerName = string.IsNullOrEmpty(containerName) ? "applog" : containerName;
CloudBlobContainer container = blobClient.GetContainerReference(containerName);
  • <appSettings> セクション自体が web.config に存在しない場合でも ConfigurationManager.AppSettings 自体は空の NameValueCollection を返すだけなので、こちらも例外にはなりません。

ご質問のコードのままで、通常のnullエラー回避としては問題ありません。

いいえ、このコードは finally を通りません。これはこれまでの回答と全く同じ理由です。

理由（再掲）

  • b / a で DivideByZeroException が発生
  • catch で捕捉され、ex.ToString() が出力される（ここは実行される）
  • throw; で再スローされる
  • この Main はエントリポイントなので、再スローされた例外を受け止める catch がどこにもない
  • → 未処理例外（unhandled exception） としてプロセスが終了する

.NET は、例外が最終的に未処理のままプロセス外まで到達する場合、通常の（catchされたときのような）スタック巻き戻し(unwind)を行いません。これはクラッシュ時の事後解析（postmortem debugging）のためにスタック情報を保持する設計上の仕様であり、.NET 2.0 以降意図的にこうなっています。

そのため、この結果として：

  • Console.WriteLine(ex.ToString()); → 実行される（catch内なので）
  • Console.WriteLine("finally"); → 実行されない（保証されない）

という動作になります。実際に実機（デバッガなし）で動かすと、コンソールには例外のスタックトレースだけが出力され、"finally" は出力されずにプロセスが異常終了するはずです（Visual Studio上でデバッガをアタッチして実行すると挙動が変わり finally が実行されることがあるので、デバッグ実行と本番実行で結果が食い違う典型例でもあります）。

finally を確実に通したい場合

catch (Exception ex)
{
    Console.WriteLine(ex.ToString());
    // throw; を外す
}
finally
{
    Console.WriteLine("finally"); // これで確実に実行される
}

throw; を残したまま finally の処理を確実に実行したいなら、前回同様、catch 内に明示的にその処理を書くのが確実です。

実際の挙動（正しい説明）

.NET の例外処理は内部的に「2パス方式」になっています。

第1パス（検索）：例外が発生すると、スタックを下から上にたどりながら、対応する catch があるか探します。この段階ではまだスタックの巻き戻し（unwind）は行われません。

ハンドラが見つからない場合：どこにも catch が無ければ、CLRはその時点で「ハンドルされていない例外」を検出し、既定の未処理例外ハンドラが動いて、コンソールに ハンドルされていない例外: ... を出力します（これがログの2番目のブロックです）。

第2パス（巻き戻し）：その後、CLRは実際にスタックを巻き戻していきます。このとき、通過する各フレームの finally ブロックが実行されます。そして最後にプロセスが終了します。

つまり、ログの順序（①catch内のex.ToString() → ②既定の未処理例外メッセージ → ③finally）は、この2パスの流れとまさに一致しています。通常の管理例外であれば、たとえ最終的に未処理でも finally は実行される、というのが正確な結論です。

では、いつ finally が通らないのか

以下のような巻き戻し自体が行えない／行われない特殊なケースに限られます。

  • StackOverflowException（スタックが尽きているので巻き戻し不可能、即プロセス終了）
  • Environment.FailFast() を呼んだ場合（意図的に巻き戻しをスキップして終了）
  • ネイティブコード側のクラッシュ（アクセス違反など）
  • プロセスを強制終了（タスクマネージャでkill、Process.Kill() など）
  • デバッガをアタッチしていて、未処理例外の時点でVisual Studioが一時停止し、そのままデバッグを終了（停止ボタン）してしまった場合 → この場合はプロセスが強制終了されるので finally は実行されない

（前回「デバッガをアタッチすると finally が実行されることがある」と書きましたが、これは逆で、デバッガ環境の方がむしろ finally が実行されずに終わりやすい（例外ダイアログで停止して終了させてしまうため）というのが実態に近いです。）

WebJobのケースへの影響

以上を踏まえると、最初の質問の SetStatus() は、finally に置いたままで、通常の（デバッガなしの）本番実行であれば実行される可能性が高いです。ただし、Azure WebJobsの実行環境（sandbox process、タイムアウトによるkillなど）によっては、通常のコンソールアプリと異なる終了のされ方をする可能性もあるため、catch 内にも明示的に呼んでおくという前回の対策自体は、保険として無駄ではありません。

いいえ、そのままでは意図通りに動きません。原因はGitの仕様上よくある落とし穴です。

問題点

.gitignore に .vs（スラッシュなし）という記述があると、これは **/.vs と同じ意味になり、.vs という名前のディレクトリ自体を丸ごと除外対象にします。

Gitは「除外されたディレクトリの中身」については、個別ファイルの否定（!）パターンがあっても中身を走査しません。つまり、

!/forstaff/.vs/forstaff/config/applicationhost.config

という1行だけを追加しても、その親である /forstaff/.vs/ 自体がすでに除外対象なので、Gitはそのディレクトリの中に入っていかず、否定パターンが無視されます。

これは公式ドキュメントにも明記されている挙動です。

It is not possible to re-include a file if a parent directory of that file is excluded.

正しい書き方

「否定したいファイルに至るまでの、すべての親ディレクトリ」を段階的に否定してあげる必要があります。また、途中の階層を丸ごと復活させると余計なファイルまで追跡対象になってしまうため、ディレクトリ名/* で中身を再度除外しつつ、次の階層だけをまた否定する、という書き方をします。

【.gitignore（.vs関連部分の修正）】
.vs
!/forstaff/.vs/
/forstaff/.vs/*
!/forstaff/.vs/forstaff/
/forstaff/.vs/forstaff/*
!/forstaff/.vs/forstaff/config/
/forstaff/.vs/forstaff/config/*
!/forstaff/.vs/forstaff/config/applicationhost.config

各行の意味

  • .vs → まず .vs という名前のディレクトリを全体除外（元の設定のまま）
  • !/forstaff/.vs/ → /forstaff/.vs/ というディレクトリ自体は除外解除（中身はまだ全部除外中）
  • /forstaff/.vs/* → その直下の中身は改めて全部除外
  • !/forstaff/.vs/forstaff/ → その中の forstaff ディレクトリだけ除外解除
  • /forstaff/.vs/forstaff/* → さらにその直下を全部除外
  • !/forstaff/.vs/forstaff/config/ → config ディレクトリだけ除外解除
  • /forstaff/.vs/forstaff/config/* → その直下を全部除外
  • !/forstaff/.vs/forstaff/config/applicationhost.config → 最後に目的のファイルだけ除外解除

このように1階層ずつ「ディレクトリを解除→中身を除外→次のディレクトリを解除」を繰り返すことで、目的のファイルだけを履歴管理対象にできます。

注意点

  • すでに .vs フォルダがGitの追跡対象外のまま長期間運用されている場合、この設定変更だけでは新規追加として認識されないことがあります。必要に応じて git add -f /forstaff/.vs/forstaff/config/applicationhost.config で明示的に追加してください。
  • applicationhost.config にはローカル環境固有のパス（ポート番号やSSL証明書のハッシュ値など）が含まれることが多く、チームで共有すると環境依存の差分が頻繁にコンフリクトを起こす可能性があります。運用上、本当にこのファイルを共有すべきかは一度チーム内で検討することをおすすめします。

はい、ご認識の通りです。MemoryStream は不要で、以下のコードだけで完結します。

理由

現在のコードには重複した処理が含まれています。

using (var memoryStream = new MemoryStream())
{
    blockBlob.DownloadToStream(memoryStream);      // ①ストリームにダウンロード（結果は使われていない）
    fileBytes = new byte[blockBlob.Properties.Length];
    blockBlob.DownloadToByteArray(fileBytes, 0);   // ②バイト配列に再ダウンロード
}
  • DownloadToStream(memoryStream) で一度BLOBの中身を memoryStream に読み込んでいますが、この後 memoryStream は一切参照されておらず、ダウンロードした内容がそのまま使われずに捨てられています
  • fileBytes に実際に格納されるデータは、直後の DownloadToByteArray(fileBytes, 0) によるもので、こちらは独立してもう一度サーバーからBLOBをダウンロードし直しています

つまり、現在のコードは同じBLOBを2回ダウンロードしている（通信の無駄）状態で、memoryStream は完全に不要な変数です。

修正後のコード

if (document.UploadFlg == true)
{
    //パス指定[会社コード/年度/従業員コード/]
    var filePath = string.Format("{0}/{1}/{2}/", companyCd, year, staffCd.Trim());
    //ストレージから取得                     
    CloudBlockBlob blockBlob = containerPdf.GetBlockBlobReference(filePath + document.FileName);

    if (blockBlob?.Exists() != true)
        return;

    // データを読み込むバイト配列の初期化。
    fileBytes = new byte[blockBlob.Properties.Length];
    // データをバイト配列に読み込む。
    blockBlob.DownloadToByteArray(fileBytes, 0);
}

DownloadToByteArray は内部で byte[] に直接書き込むため、MemoryStream を経由する必要がありません。この修正により、通信回数が半分（1回）に減り、コードもシンプルになります。

補足

blockBlob.Properties.Length を使う前に FetchAttributes() が必要になる場合がありますが、直前で Exists() を呼んでいるため、SDKの実装上 Exists() 内部で FetchAttributes 相当の処理が行われ Properties が更新されるので、このままで問題なく動作するはずです（お使いのSDKバージョンで念のため実機確認はしておくと安心です）。

MemoryStream を使う場合は、DownloadToStream でストリームに書き込んだ後、ToArray() で byte[] に変換する形になります。

コード例

if (document.UploadFlg == true)
{
    //パス指定[会社コード/年度/従業員コード/]
    var filePath = string.Format("{0}/{1}/{2}/", companyCd, year, staffCd.Trim());
    //ストレージから取得                     
    CloudBlockBlob blockBlob = containerPdf.GetBlockBlobReference(filePath + document.FileName);

    if (blockBlob?.Exists() != true)
        return;

    // BLOBをストリームに取り込み、配列に格納する
    using (var memoryStream = new MemoryStream())
    {
        blockBlob.DownloadToStream(memoryStream);
        fileBytes = memoryStream.ToArray();
    }
}

ポイント

  • DownloadToStream(memoryStream) でBLOBの内容が memoryStream の内部バッファに書き込まれます
  • memoryStream.ToArray() で、書き込まれた範囲（Position ではなく Length 分）だけを新しい byte[] としてコピーして返します
  • ToArray() は内部で新しい配列を確保してコピーするため、事前に配列サイズ（blockBlob.Properties.Length）を用意しておく必要はありません

DownloadToByteArray 方式との比較

観点DownloadToByteArray（前回の方法）MemoryStream + ToArray()（今回の方法）
事前準備Properties.Length でサイズ確保が必要不要（ストリームが自動拡張）
メモリ効率配列に直接書き込むため無駄が少ない内部バッファ→ToArray()でコピーが発生し、一時的にメモリを多く使う
コード量やや少ないわずかに増える（usingが必要）

用途上どちらでも最終結果（fileBytes の中身）は同じになりますが、単にBLOBを丸ごとバイト配列として取得したいだけなら、DownloadToByteArray の方がメモリ効率がよく、コードもシンプルです。MemoryStream 経由が有効なのは、たとえば「ダウンロードしたストリームを他のAPI（Stream を引数に取るもの）にそのまま渡したい」場合など、Stream として扱う必要がある場面です。

1. PdfSmartCopy → PdfCopy への変更（最も効果が大きい可能性が高い）

PdfSmartCopy は、結合対象のPDF間で同一のフォント・画像などのリソースをバイト単位で比較し重複除去するという処理を行っています。これは出力ファイルサイズを小さくできる利点がありますが、比較処理自体にコストがかかるため、結合対象のPDFがそれぞれ独立していてリソースを共有していない場合（＝重複除去の恩恵がほぼない場合）、この比較コストが丸ごと無駄になり、処理速度を大きく落とします。

単に複数PDFを連結するだけで重複除去が不要であれば、PdfCopy に変更するだけで速度改善が見込めます。

// PdfSmartCopy pdfCopy = null;
PdfCopy pdfCopy = null;
// ...
// pdfCopy = new PdfSmartCopy(doc, fs);
pdfCopy = new PdfCopy(doc, fs);

トレードオフとして、共通フォントなどを埋め込んでいる複数PDFを結合する場合は出力ファイルサイズが大きくなる可能性があります。速度とファイルサイズのどちらを優先するかで判断してください。

2. Blobダウンロード由来なら、一時ファイルを経由せず byte[] から直接結合する

以前のやり取りの流れからすると、結合対象のPDFはAzure Storageからダウンロードしたものかと思います。もし現状「Blob→一時ファイルに書き出し→MargePdfにファイルパスを渡す→PdfReaderがファイルを再度読み込む」という流れになっているなら、ディスクへの書き込みと読み込みが余分に発生しています。

PdfReader は byte[] を直接受け取れるので、ダウンロードした fileBytes をそのまま渡せば、ディスクI/Oを1往復まるごと削減できます。

                    pdfCopy.AddPage(page);
                }
            }
            finally
            {
                try { reader?.Close(); } catch { }
            }
        }

    }
    catch (Exception ex)
    {
        errorProc err = new errorProc();
        err.ErrLog("makePdfs.MargePdf", ex);

    }

    {
        try { pdfCopy?.Close(); } catch { }
        try { doc?.Close(); } catch { }

なぜ改善になるか

  • Assembly.LoadFrom は同じアセンブリを実質的に何度も読み込もうとする無駄な処理です（.NETは同一パスの再ロードを内部的に回避しますが、その判定コスト自体は毎回発生します）
  • BaseFont.AddToResourceSearch は内部的にリストへパスを追加する処理で、呼び出すたびに同じパスが重複してリストに追加され続け、リストが肥大化していきます（実害は軽微ですが無意味な処理です）
  • BaseFont.CreateFont は指定した埋め込みフォント（この場合はCID日本語フォント）をパースして BaseFont インスタンスを構築する処理で、このコストが最も高く、PDF出力のたびに毎回発生しているなら明確なボトルネックになりえます
  • BaseFont インスタンス自体はスレッドセーフに読み取り専用で使い回せる設計になっているため、一度生成して使い回すことは itextsharp の想定内の使い方です

実装方法：静的コンストラクタより Lazy<T> が安全

静的コンストラクタ（static ClassName() { ... }）でも動作しますが、注意点があります。

静的コンストラクタで例外が発生すると、TypeInitializationException にラップされ、以後そのクラスへのアクセスは（アプリケーションドメインが存続する限り）ずっと失敗し続けます。たとえば一時的なファイルロック等でフォント読み込みに失敗した場合、リトライが一切できなくなり、プロセス再起動までPDF出力機能全体が使えなくなるリスクがあります。

そのため、Lazy<BaseFont> を使う方法をおすすめします。

public static class PdfFontHelper
{
    private static readonly Lazy<BaseFont> _japaneseFont =
        new Lazy<BaseFont>(CreateJapaneseFont, LazyThreadSafetyMode.ExecutionAndPublication);

    public static BaseFont JapaneseFont => _japaneseFont.Value;

    private static BaseFont CreateJapaneseFont()
    {
        string dllPath = HostingEnvironment.MapPath("~") + @"\bin\lib\iTextAsian-1.0.dll";
        System.Reflection.Assembly.LoadFrom(dllPath);
        BaseFont.AddToResourceSearch(dllPath);
        return BaseFont.CreateFont("HeiseiKakuGo-W5", "UniJIS-UCS2-H", BaseFont.EMBEDDED);
    }
}

呼び出し側は次のように変更するだけです。

// 変更前
// BaseFont baseFont = BaseFont.CreateFont(...);

// 変更後
BaseFont baseFont = PdfFontHelper.JapaneseFont;

Lazy<T> を使うメリット

  • スレッドセーフ：LazyThreadSafetyMode.ExecutionAndPublication により、複数スレッドから同時にアクセスされても初期化処理は1回だけ実行される
  • 初回失敗時にリトライ可能：Lazy<T> は例外発生時、既定では例外をキャッシュして以後も同じ例外を返しますが、必要であれば LazyThreadSafetyMode.PublicationOnly を使うことで失敗時に再試行させる挙動に変更できます（要件次第）
  • 静的コンストラクタと違い、実際に JapaneseFont に初めてアクセスしたタイミングで初期化される（不要な場面でクラスをロードしても初期化コストがかからない）

補足：BaseFont を複数種類使っている場合

もしゴシック体・明朝体など複数のフォントを使い分けているなら、同様に Lazy<BaseFont> のフィールドをフォントごとに用意すれば、それぞれ初回アクセス時にのみ初期化されるようにできます。

この変更により、PDF出力のたびに発生していたフォント解析コストがアプリケーション（またはApp Pool）の生存期間中に1回だけに減るため、特に大量のPDFを連続出力するバッチ処理では体感できるレベルの速度改善が期待できます。

問題点

public static readonly Lazy<BaseFont> japaneseFont = 
    new Lazy<BaseFont>(CreateJapaneseFont, LazyThreadSafetyMode.ExecutionAndPublication).Value;

このコードは、右辺の型が .Value の分だけ変わってしまっています。

  • new Lazy<BaseFont>(...) → Lazy<BaseFont> 型のインスタンスを生成
  • .Value → その場で即座に評価を実行し、中身の BaseFont を取り出す

つまり .Value を付けた時点で、CreateJapaneseFont() がフィールド初期化のタイミングで即座に呼ばれてしまいます。その結果、左辺の型 Lazy<BaseFont> と右辺の型 BaseFont が一致せず、コンパイルエラーになります。

エラー CS0029: 型 'iTextSharp.text.pdf.BaseFont' を 'System.Lazy<iTextSharp.text.pdf.BaseFont>' に暗黙的に変換できません

そもそもの意図とのズレ

Lazy<T> を使う目的は「実際に使われるまで初期化を遅延させる」ことでした。.Value をその場で呼んでしまうと、静的フィールドの初期化時（＝クラスが最初にロードされたタイミング）に即座に CreateJapaneseFont() が実行されることになり、これは実質的に静的コンストラクタで直接生成するのとほぼ同じ挙動になってしまいます（例外時にクラス全体が使用不能になるリスクも同様に残ります）。

正しい書き方（1行にまとめたい場合）

型を Lazy<BaseFont> のまま保持し、.Value は呼び出し側で使うようにします。

public static readonly Lazy<BaseFont> JapaneseFont = 
    new Lazy<BaseFont>(CreateJapaneseFont, LazyThreadSafetyMode.ExecutionAndPublication);

呼び出し側：

BaseFont baseFont = PdfFontHelper.JapaneseFont.Value;

前回提示したコードのようにプロパティでラップして .Value を隠す方法（public static BaseFont JapaneseFont => _japaneseFont.Value;）にすれば、呼び出し側で .Value を書かずに済み、かつ遅延初期化の恩恵もそのまま得られるので、そちらの方が使い勝手は良いです。お好みでどちらでも問題ありません。

    public static bool MargePdf(...)

        BaseFont baseFont = _japaneseFont.Value;

    }

わざわざ別クラスを作らず、既存クラスに数行足すだけで済みます。

分離したほうがよいケース

以下のような状況であれば、別クラス（PdfFontHelper など）に分離する価値があります。

  • BaseFont を使う処理が MargePdf 以外にも複数のクラスに散らばっている（例：PDF結合処理、PDF新規生成処理、別のバッチ処理など、複数箇所で同じ日本語フォントを使い回したい）
  • 別クラスに分離しないと、各クラスがそれぞれ独自に Lazy<BaseFont> を持ってしまい、結局フォントが複数回初期化されてしまう（今回の「至る箇所で実行されている」という元々の問題が、粒度を変えて再発する）

「至る箇所で実行されている」というご質問の背景からすると、既に複数のメソッド・クラスにまたがってこのコードが書かれている可能性が高いので、その場合は共通の1箇所（PdfFontHelperのような静的クラス）にまとめておいたほうが、今後同じ問題を繰り返さずに済みます。

結論

  • 使用箇所が1クラスに閉じている → 分離不要、そのクラス内に static readonly Lazy<BaseFont> を追加するだけでよい
  • 使用箇所が複数クラスにまたがっている → 分離しておいたほうが、初期化の一元管理ができて安全

ご自身のプロジェクトで実際に何箇所・何クラスから呼ばれているかによって判断してください。

private static readonly Lazy<BaseFont> _japaneseFont = ...

このコメントは「動作（作成する）」の説明になっていますが、実際にこの行自体がやっているのは「Lazy<BaseFont> という遅延初期化用の入れ物を用意する」ことです。「作成する」という動作が実際に走るのは、後で誰かが .Value（＝JapaneseFont プロパティ）にアクセスした瞬間であり、このフィールド宣言の時点ではまだ何も作られません。

なので、コメントとしては「フィールドが何であるか」を説明する形にした方が正確です。

修正案

/// <summary>
/// 日本語フォント（HeiseiKakuGo-W5）の遅延生成用インスタンス。
/// 初回アクセス時にのみ <see cref="CreateJapaneseFont"/> が実行され、以降は生成結果を再利用します。
/// </summary>
private static readonly Lazy<BaseFont> _japaneseFont =
    new Lazy<BaseFont>(CreateJapaneseFont, LazyThreadSafetyMode.ExecutionAndPublication);

/// <summary>
/// 日本語フォント（HeiseiKakuGo-W5）を取得します。未生成の場合はこの時点で生成されます。
/// </summary>
public static BaseFont JapaneseFont => _japaneseFont.Value;

/// <summary>
/// 日本語フォント（HeiseiKakuGo-W5）を生成します。
/// </summary>
/// <returns>生成した <see cref="BaseFont"/> インスタンス。</returns>
private static BaseFont CreateJapaneseFont()
{
    string dllPath = HostingEnvironment.MapPath("~") + @"\bin\lib\iTextAsian-1.0.dll";
    System.Reflection.Assembly.LoadFrom(dllPath);
    BaseFont.AddToResourceSearch(dllPath);
    return BaseFont.CreateFont("HeiseiKakuGo-W5", "UniJIS-UCS2-H", BaseFont.EMBEDDED);
}

変更のポイント

  • _japaneseFont：「作成します」という動作の説明から、「遅延生成用インスタンス」というフィールドの正体の説明に変更し、あわせて「初回アクセス時にのみ生成される」という Lazy 特有の重要な性質を明記
  • JapaneseFont：単に「取得します」だけだと、実は初回だけ内部で生成処理が走るという重要な副作用が伝わらないため、一言補足を追加
  • CreateJapaneseFont：ほぼそのままで問題ありませんが、<returns> の中身が空だったので説明を追加し、他の2つと表現の粒度を揃えました

JapaneseFont と CreateJapaneseFont のコメントは元々の内容でも意味として大きな誤りはないので、最低限直すべきは _japaneseFont 側のコメントです。

あなた

ワーカープロセスがリサイクルされた場合、CreateJapaneseFontは正しく実行されますか？

Claude

はい、正しく実行されます。

理由

static readonly フィールドや Lazy<T> は、プロセス（正確にはAppDomain）単位で状態を保持しています。ワーカープロセス（w3wp.exe）がリサイクルされると、これは基本的に新しいプロセスが新規に起動されることを意味するため、以前のプロセスで保持していた静的フィールドの状態（初期化済みの BaseFont インスタンスなど）はすべて破棄され、新しいプロセスではまっさらな状態から始まります。

つまり：

  • リサイクル後、新しいプロセスで PdfFontHelper クラスが最初にロードされる
  • _japaneseFont フィールドは未初期化の Lazy<BaseFont> として新規に作られる
  • その後、誰かが最初に JapaneseFont にアクセスしたタイミングで CreateJapaneseFont() が実行され、フォントが再生成される

という流れになり、意図通り正しく動作します。リサイクル前のプロセスで例外が発生してキャッシュされていたとしても、新しいプロセスには一切引き継がれないため、「リサイクルしても直らない」といった心配は不要です。

補足：オーバーラップリサイクルの場合の注意点

IIS の既定設定では「オーバーラップ・リサイクル（Overlapped Recycle）」が有効になっていることが多く、この場合は古いプロセスと新しいプロセスが一時的に同時に稼働します。

  • 新しいプロセスが起動し、リクエストを受け付けられる準備ができるまで
  • 古いプロセスは（設定されたシャットダウンタイムリミットの間）既存のリクエストを処理し続ける

という重なりが発生します。これは今回の Lazy<BaseFont> の話には直接影響しません（お互いのプロセスは完全に独立したメモリ空間を持つため）。ただし、リサイクル直後の新プロセスへの最初のPDF出力リクエストは、フォント生成のコストを毎回払うことになる（＝いわゆるコールドスタート）点は認識しておくとよいです。頻繁にリサイクルが起きる環境（メモリ上限によるリサイクルなど）であれば、その都度このコストが発生します。

まとめ

  • 動作の正しさという観点では、リサイクルされても Lazy<BaseFont> は問題なく機能し、新しいプロセスで正しく再生成されます
  • パフォーマンスという観点では、リサイクル直後の初回アクセス時だけ生成コストがかかりますが、これは元々の「毎回生成していた」状態からは大幅に改善されており、問題視するレベルではありません
あなた

何らかの理由でCreateJapaneseFont関数で例外が発生した場合、次のアクセスで再度実行されますか？

Claude

いいえ、既定の設定（LazyThreadSafetyMode.ExecutionAndPublication）のままでは再実行されません。

理由

Lazy<T> は、初回の評価（ファクトリメソッドの実行）で例外が発生した場合、その例外自体をキャッシュします。そして、以後 .Value にアクセスするたびに、CreateJapaneseFont() を再実行するのではなく、キャッシュしておいた同じ例外を再スローします。

これは ExecutionAndPublication と PublicationOnly の両方の初期化モードで共通の挙動です（None モードでも同様に例外はキャッシュされます）。つまり、一度失敗すると、そのAppDomain（プロセス）が存続する限り、JapaneseFont へのアクセスは永久に同じ例外を吐き続けることになります。ワーカープロセスがリサイクルされない限り復旧しません。

対処法：LazyThreadSafetyMode.PublicationOnly を使う

PublicationOnly モードにすると、例外発生時のキャッシュを回避できます。

private static readonly Lazy<BaseFont> _japaneseFont =
    new Lazy<BaseFont>(CreateJapaneseFont, LazyThreadSafetyMode.PublicationOnly);

このモードの挙動は以下の通りです。

  • 複数スレッドが同時に初回アクセスした場合、それぞれのスレッドが個別に CreateJapaneseFont() を実行してしまう（ExecutionAndPublication は1スレッドだけが実行し他は待機するのに対し、こちらは早い者勝ちで結果を採用する方式）
  • ただし、例外が発生した場合はキャッシュされず、次に .Value にアクセスしたときに再度 CreateJapaneseFont() が実行される
  • 成功した場合は、最初に完了したスレッドの結果が採用され、以後はその結果が使い回される（他のスレッドが並行して計算していた分は破棄される）

トレードオフ

PublicationOnly は「例外時にリトライできる」というメリットがある一方、「成功するまでの間、複数リクエストが同時に来ると、同じ重い処理（ファイル読み込み・フォント解析）が複数回並行して走る可能性がある」というデメリットがあります。今回の CreateJapaneseFont はファイル読み込みを伴う処理なので、アクセス頻度が高い起動直後のタイミングで複数リクエストが重なると、一時的に処理が重複する可能性があります。

実務上の判断

  • フォントファイルの読み込み失敗は、通常は「デプロイミス」や「パス設定ミス」など、リトライしても直らない場合がほとんど（ファイルが存在しない、パスが間違っている等）なので、ExecutionAndPublication のまま「一度失敗したら次のデプロイ・リサイクルまで直らない」という挙動でも実害は小さいことが多いです
  • 一方で、一時的なファイルロック競合などタイミング依存の失敗がありうる場合や、「1回失敗しても自動復旧してほしい」という要件があるなら PublicationOnly に変更する価値があります

どちらのモードを選ぶかは、失敗の原因がリトライで解消しうるものかどうかで判断するとよいと思います。今回のケース（DLLパス・フォント名が固定されている静的な設定）であれば、個人的には ExecutionAndPublication のままで問題ないと考えますが、運用上「PDF出力が全滅したらすぐ気づける監視体制があるか」も合わせて検討されるとよいかと思います。
