中戸川
azureのapp serviceで.net mvcのサービスを稼働しており、リクエストを処理中にデプロイするとリクエストはどうなりますか？
Claude

デプロイ方法による違い

通常のデプロイ（標準デプロイ）の場合: 処理中のリクエストは中断される可能性が高いです。デプロイ時にアプリケーションプールが再起動されるため、進行中のリクエストは以下のようになります:
  • 処理中のリクエストは途中で切断される
  • クライアント側ではタイムアウトやエラーが発生する
  • データベーストランザクション中の場合、ロールバックされる可能性がある
スロット機能を使用したデプロイの場合: より安全にデプロイできます:
  1. ステージングスロットに新しいバージョンをデプロイ
  2. ウォームアップが完了してからスワップ
  3. スワップ時も既存のリクエストは処理を継続（ただし完全な保証はない）

推奨される対策

  • デプロイスロットを使用してスワップデプロイを実行
  • Application Initializationモジュールを設定してウォームアップ時間を確保
  • メンテナンスウィンドウを設けて、トラフィックが少ない時間帯にデプロイ
  • ヘルスチェックエンドポイントを設定してスワップのタイミングを最適化
  • 長時間実行されるリクエストは、バックグラウンドジョブやキュー処理に分離
デプロイスロットの設定により、ダウンタイムをほぼゼロにすることが可能です。

  • 設定 → 「ダウンロード」

試してみる対処法

  • Chromeの再起動

  • Chromeを最新版に更新

fetchでblobをダウンロードする実装にしています。 .then(function (result) { var objURL = window.URL.createObjectURL(result.blob); var a = document.createElement('a'); a.href = objURL; a.download = result.filename; a.click(); window.URL.revokeObjectURL(objURL); });
Claude
Android Chromeでは、a.click()が即座に実行されても反応が鈍い、またはrevokeObjectURLのタイミングが早すぎる可能性があります。 以下のように修正してみてください： 
.then(function (result) {
    var objURL = window.URL.createObjectURL(result.blob);
    var a = document.createElement('a');
    a.href = objURL;
    a.download = result.filename;

    document.body.appendChild(a);
    a.click();

    setTimeout(function() {
        document.body.removeChild(a);
        window.URL.revokeObjectURL(objURL);
    }, 100);
});

ポイント

  • revokeObjectURLを即座に呼ぶと、ダウンロードが開始される前にURLが無効化される
  • Android Chromeは処理が遅延する傾向があるため、setTimeoutで少し待つ
  • 要素をDOMに追加することで、より確実にクリックイベントが処理される

ダウンロードを非同期処理でローディングを表示したいです。
Claude
なるほど、非同期処理でローディング表示が必要なケースですね。それならFetch + Blobの実装が適切です。 
showLoading();

fetch(url)
.then(function(response) {
    if (!response.ok) throw new Error('ダウンロードに失敗しました');

    var contentDisposition = response.headers.get('Content-Disposition');
    var filename = 'download.pdf';
    if (contentDisposition) {
        var matches = /filename[^;=\n]*=((['"]).*?\2|[^;\n]*)/.exec(contentDisposition);
        if (matches && matches[1]) {
            filename = decodeURIComponent(matches[1].replace(/['"]/g, ''));
        }
    }

    return response.blob().then(function(blob) {
        return { blob: blob, filename: filename };
    });
})
.then(function(result) {
    var objURL = window.URL.createObjectURL(result.blob);
    var a = document.createElement('a');
    a.href = objURL;
    a.download = result.filename;
    a.style.display = 'none';

    document.body.appendChild(a);
    a.click();

    setTimeout(function() {
        document.body.removeChild(a);
        window.URL.revokeObjectURL(objURL);
        hideLoading();
    }, 100);
})
.catch(function(error) {
    hideLoading();
    console.error('ダウンロードエラー:', error);
    alert('ダウンロードに失敗しました');
});

問題の正体

ダウンロード自体は成功しており、Android Chromeの「ダウンロード完了後の通知・反応」の問題だったということですね。
  • ダウンロード自体は成功している
  • 保存先確認をオンにすると、明示的にダイアログが出るため「反応がある」
  • 保存先確認がオフだと、バックグラウンドで保存されるだけで通知が出ない・分かりにくい

最近のChromeの仕様

最近のAndroid Chromeでは、ダウンロード完了時の通知が控えめになっています。通知が出ない、または一瞬で消える・ダウンロードバーが表示されないケースがあります。 コードを修正する必要はなく、ユーザー向けにUI上でフィードバックを追加するか（「ダウンロードフォルダをご確認ください」など）、そのままでもOKです。

潜在的な問題点

var filename = 'download.pdf';

// filename*=UTF-8'' を優先
var utf8Match = disposition.match(/filename\*=UTF-8''([^;]+)/i);
if (utf8Match) {
    filename = decodeURIComponent(utf8Match[1]);
} else {
    var normalMatch = disposition.match(/filename=["']?([^;"']+)["']?/i);
    if (normalMatch) {
        filename = normalMatch[1];
    }
}

Content-Disposition: attachment; filename="test.pdf"; other-param=value となることは多々ありますか？
Claude
いいえ、ほとんどありません。追加パラメータが付くことは極めて稀です。

よく見るフォーマット

Content-Disposition: attachment; filename="test.pdf"
Content-Disposition: attachment; filename=test.pdf
Content-Disposition: attachment; filename*=UTF-8''%E3%83%86%E3%82%B9%E3%83%88.pdf
Content-Disposition: attachment; filename="test.pdf"; filename*=UTF-8''%E3%83%86%E3%82%B9%E3%83%88.pdf
最後のパターン（filenameとfilename*の両方）はブラウザ互換性のために両方指定するケースで、これは実際によくあります。 元のコードで問題になりうるのは Content-Disposition: attachmentのみ（filenameなし）のケースで、undefinedエラーになります。最低限 undefinedチェックを追加するだけで安全になります。

中戸川
a.click(); window.URL.revokeObjectURL(objURL); は非同期で実行されますか？
Claude
いいえ、同期的に実行されます。

実行順序

a.click();                           // 1. 同期実行（ダウンロード開始をトリガー）
window.URL.revokeObjectURL(objURL);  // 2. 同期実行（URLを即座に無効化）
alert('ダウンロードを開始しました');    // 3. 同期実行

問題点

a.click()はダウンロードを開始するトリガーを発行するだけで、実際のダウンロード処理はブラウザが非同期で行います。そのため即座にrevokeObjectURLを呼ぶと、特にAndroid Chromeのように処理が遅いブラウザで問題になる可能性があります。 setTimeoutで100ms程度遅延させることを推奨します。
中戸川
android+chromeでrevokeObjectURLを遅延させなくてもダウンロードできています。choromeのバージョンに依存しますか？
Claude
はい、Chromeのバージョンや実装に依存します。 最近のChrome（特にAndroid版）はパフォーマンス改善により、a.click()時点でBlobを即座に処理する傾向があり、revokeObjectURLを遅延させなくても動作することが多いです。 現在の環境（Android Chrome最新版）で動作しているなら問題ありませんが、setTimeoutを入れることのデメリットはほぼゼロなので、クロスブラウザ・将来の互換性のために入れておく方が安全です。
中戸川
revokeObjectURLを2回目以降実行した際に前回のobjURLをrevokeObjectURLすればいいのではないですか？
Claude
その通りです！非常に良いアイデアです。 
var previousObjectURL = null;

.then(function (result) {
    // 前回のURLがあればクリーンアップ
    if (previousObjectURL) {
        window.URL.revokeObjectURL(previousObjectURL);
    }

    var objURL = window.URL.createObjectURL(result.blob);
    var a = document.createElement('a');
    a.href = objURL;
    a.download = result.filename;
    a.click();

    previousObjectURL = objURL;
});

メリット

  • ✅ setTimeoutが不要
  • ✅ 確実にダウンロードが完了してからクリーンアップ
  • ✅ メモリリークを防げる

注意点

最後のURLがクリーンアップされないため、ページ離脱時に処理が必要です： 
window.addEventListener('beforeunload', function() {
    if (previousObjectURL) {
        window.URL.revokeObjectURL(previousObjectURL);
    }
});
